# ADR-002: Persistence & ORM Strategy

Status: Accepted
Date: 2026-09-22

## Context

v0.1 uses SQLite, running locally, per ARCHITECTURE.md. The architecture requires that a future migration to PostgreSQL not require rewriting the Service Layer or any layer above it. Only the Repository/Data Access Layer is permitted to know the persistence implementation (ARCHITECTURE.md §1).

## Decision

Use SQLAlchemy 2.x (Core + ORM) as the ORM/query layer, confined entirely to the Repository Layer, with Alembic for versioned schema migrations.

## Rationale

- SQLAlchemy has mature, well-tested support for both SQLite and PostgreSQL, directly serving the migration path described in ARCHITECTURE.md §7.
- Typed column definitions support `Decimal`-backed numeric columns and UUID primary keys (see ADR-005, ADR-007) without ad hoc handling.
- Alembic produces versioned, reviewable migration scripts. Autogenerated migrations are never trusted blindly — especially for monetary columns — and require explicit review before being applied.

## Alternatives Considered

- **Raw SQL / no ORM**: simpler mental model, but pushes all SQLite/PostgreSQL dialect-handling work onto hand-written, per-database SQL, increasing the risk and scope of the Repository Layer's responsibilities.
- **TypeScript ORMs (Drizzle, Prisma)**: not applicable, since Python was selected as the core language (ADR-001). Prisma specifically was noted as carrying a vendor lock-in risk via its generated query-engine binary, relevant only if TypeScript were chosen.

## Consequences

- All SQL/ORM code lives inside Repository Layer modules; the Service Layer and everything above it never imports SQLAlchemy directly and works only with plain domain objects.
- Migrating to PostgreSQL means changing connection configuration, adjusting some dialect-specific column behavior, and adding PostgreSQL-specific migration scripts — not rewriting the Service Layer, MCP/REST adapters, or business logic (per ARCHITECTURE.md §7's honestly-scoped guarantee).

## Constraints

- SQLAlchemy and Alembic must not be imported or referenced outside the Repository Layer.
- Any migration touching a monetary column requires explicit human review (or AI-proposed, human-approved review) before being applied; autogenerated migrations are never accepted unreviewed for such columns.

## Revisit Triggers

- SQLAlchemy failing to adequately abstract a PostgreSQL-specific feature the system comes to need.
- Performance requirements emerging that SQLAlchemy cannot reasonably meet.
- A future decision to move away from Python (which would supersede this ADR along with ADR-001).
